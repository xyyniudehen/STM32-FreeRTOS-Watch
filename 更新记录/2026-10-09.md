# 2026-10-08～2026-10-09 Bootloader DMA接收与OLED升级进度归档

## 变更摘要

本轮将Bootloader固件数据包接收从CPU逐字节查询改为UART RX DMA普通模式，并进一步由DMA完成/错误中断报告结果。保留逐包应答、CPU阻塞等待、Flash半字编程与整固件CRC32校验，用户已验证DMA回显、分段接收、超时和固件升级成功。新增接收错误分类和跳转APP前DMA资源清理，接入软件SPI OLED等待界面、写入进度和成功提示。过程中确认并修复APP初始化覆盖VTOR的问题，另发现OLED加入后Boot曾超出16KiB并与APP重叠；现有Map显示Boot回到13.25KiB，但EIDE配置差异、显示前导零和字库裁剪仍需核实。

范围：仓库根目录为`14freertos/RTOS`，Boot工程位于`Bootloader/`。依据当前源码、现有构建产物及10月8～9日对话，不代表重新执行了全套实机测试。前期修改在`11/12串口boot`进行，后合并至当前仓库；下面路径均相对当前仓库根目录。

### 3. 函数调用树：谁调用谁

从Boot入口沿一棵主树看到升级与APP跳转。一级阶段之间用竖线空行留白，二级调用保持紧凑；节点只附短职责。缩进表示直接调用，条件和重复调用在节点中注明；只展开本轮关键路径。

#### 3.1 完整主调用树

```text
main()：启动Boot，等待U，选择升级或启动APP
│
├── Serial_Init()：初始化UART、DMA时钟和DMA中断入口
├── OLED_Init()：初始化SPI引脚和OLED控制器
├── OLED_Update()：显示Boot等待画面
│
├── [收到U] BootUpdate_Start()：执行一次完整升级
│   ├── BootUpdate_ClearReceiveData()：清理旧UART数据
│   ├── BootUpdate_ReceiveHeader()：接收固件长度和预期CRC
│   │   ├── BootUpdate_ReceiveByteTimeout()：逐字节等待固件头
│   │   │   └── Serial_ReceiveByte()：查询RXNE并读取DR
│   │   └── BootUpdate_GetUint32LE()：解析小端字段
│   ├── BootFlash_EraseApp()：按固件大小擦除APP页
│   ├── BootUpdate_ReceiveFirmware()：循环收包并写入Flash
│   │   ├── Serial_DMAReceiveStart()：准备当前包DMA接收
│   │   │   └── Serial_DMAReceiveStop()：清理上一包接收状态
│   │   ├── Serial_Send_String()：发送PACKET READY
│   │   ├── Serial_DMAReceiveWait()：等待DMA完成、错误或超时
│   │   │   └── Serial_DMAReceiveStop()：结束当前DMA接收
│   │   ├── [接收失败] BootUpdate_PrintReceiveError()：打印错误原因
│   │   │   └── Serial_DMAGetLastError()：读取错误分类
│   │   ├── BootFlash_Write()：半字写Flash并回读校验
│   │   ├── BootUpdate_ShowProgress()：绘制成功写入进度
│   │   │   └── OLED_Update()：通过软件SPI刷新屏幕
│   │   └── Serial_Send_String()：发送PACKET OK
│   ├── BootUpdate_CRC32()：重新计算Flash中的固件CRC
│   └── OLED_Update()：CRC通过后显示Update OK
│
└── [超时且APP有效] Boot_JumpToApp()：清理资源并启动APP
    ├── Serial_DMADeInit()：关闭Boot使用过的DMA和NVIC状态
    │   └── Serial_DMAReceiveStop()：停止DMA请求和通道
    └── app_entry()：通过函数指针执行APP Reset_Handler
```

上面是一棵完整主树：空行表示一级阶段，二级调用保持紧凑。`BootUpdate_ReceiveFirmware()`会对每个数据包重复执行收包、写Flash、刷新进度和确认。

DMA中断由硬件触发，属于主树之外的异步入口：

```text
DMA1_Channel5_IRQHandler()：DMA完成或错误时由CPU进入
├── DMA_GetITStatus()：判断TE错误或TC完成
├── DMA_ClearITPendingBit()：清除对应中断标志
└── 更新Serial_DMA_RxResult：错误写2，完成写1
```

它不是`Serial_DMAReceiveWait()`直接调用的函数；Wait只是读取ISR写入的结果。

### 4. 一包数据实际怎么走

下面是发生顺序，不是函数嵌套关系：

```text
主程序启动DMA并发送PACKET READY
    ↓
电脑发送数据，UART收到字节放进DR
    ↓
DMA自动把字节写进BootUpdate_Packet，直到收满本包
    ↓
DMA硬件产生中断，ISR把Serial_DMA_RxResult写成1
    ↓
正在等待的Serial_DMAReceiveWait读到1，关闭接收并返回成功
    ↓
主程序把RAM包写进Flash，更新OLED进度，再发PACKET OK
```

因此“交接”在这里就是一个共享结果变量：ISR写，等待函数读。Boot没有RTOS任务、队列通知或双缓冲。OLED在接收结束后刷新，当前没有接收与显示同时运行的流水线。

重点接口说明：

- `Serial_DMAReceiveStart(uint8_t *buffer, uint16_t length)`：buffer是容量至少为length的RAM地址，length是字节数；返回1只代表已启动。清旧数据和上次结果后开启DMA，必须在READY前调用。
- `Serial_DMAReceiveWait(uint32_t timeout_count)`：主程序阻塞查询ISR结果与UART错误；次数耗尽结束接收；1成功、0失败。等待仍占用CPU，不是非阻塞接口。
- `Serial_DMAReceiveStop(void)`：关闭请求、通道、TC/TE使能，清DMA和NVIC挂起，RxActive清0；不清LastError，以供错误打印。
- `DMA1_Channel5_IRQHandler(void)`：ISR优先处理TE，再处理TC，只清标志和写结果；不刷新OLED、不写Flash。NVIC抢占值2、子优先级0，实际分组需结合初始化确认。
- `Serial_DMAGetLastError(void)`：返回Serial_RxError_t最近错误；`BootUpdate_PrintReceiveError(void)`在同文件中据此打印启动或等待失败原因。
- `Serial_DMADeInit(void)`：退出Boot时禁用NVIC并复位DMA；放在切MSP之前，不用于每包结束。
- `BootUpdate_ReceiveFirmware(uint32_t firmware_size)`：计算本包有效长度，依次接收、写入、推进地址和进度；全部完成返回1，失败返回0。
- `BootUpdate_ShowProgress(uint32_t received_size, uint32_t firmware_size)`：按成功写入量计算百分比；100%仅代表写完，CRC通过后才能提示成功。

### 5. DMA、OLED和地址配置

| 配置 | 当前值/意义 |
| --- | --- |
| UART | 使用USART1外设异步模式，PA9 TX/PA10 RX，115200、8N1 |
| DMA时钟和映射 | AHB DMA1；USART1_RX对应DMA1_Channel5 |
| DMA源/目的 | USART1->DR固定地址；RAM数组地址递增 |
| 方向、宽度、数量 | 外设到RAM，两端Byte，每包最多256字节，普通模式，无M2M |
| DMA中断 | TC完成、TE错误；NVIC DMA1_Channel5_IRQn使能 |
| 长度转换 | `(uint16_t)packet_size`匹配接口与DMA计数范围，256安全；不是把字节变成Flash半字 |
| Flash写入 | CPU执行STM32F103半字编程，2字节对齐；奇数末尾补0xFF；CRC仅覆盖有效长度 |
| SPI OLED | GPIO模拟Mode 0，MSB先发，PA5 SCK、PA7 MOSI、PB6 CS、PB7 DC、PB8 RES；非硬件SPI |
| Boot/APP边界 | Boot 0x08000000～0x08003FFF；APP从0x08004000，48KiB |
| APP向量表 | VECT_TAB_OFFSET=0x4000；Boot保持0x0 |
| Python | COM10、115200、包长256，收到Update Mode停止U；收到PACKET READY发送，PACKET OK推进文件偏移 |

全局`__disable_irq()`只屏蔽CPU响应，不会停止DMA、清外设标志或清NVIC挂起请求。因此跳转前在切MSP之前调用Serial_DMADeInit，APP重新开启中断后不会继承Boot的DMA请求。

## 第三部分：真实故障与排查

### 6. 问题记录

#### 问题一：已跳入APP初始化，但FreeRTOS任务未运行

- **现象：**不做串口升级，分别下载Boot与APP，超时输出Jump App和MPU6050 init OK后不运行UI。增加__enable_irq未解决。
- **排查：**串口输出证明已执行APP普通代码；Memory窗口首两项为0x20003DC0和0x08004345；当次bin46284字节，小于49152；再检查启动文件和SystemInit对VTOR的写入。
- **已确认根因：**Boot设VTOR=0x08004000，APP SystemInit使用偏移0x0又改回0x08000000。RTOS的SVC等异常查到Boot向量，而普通初始化仍可执行。
- **修复/结果：**APP偏移改0x4000，用户确认运行恢复。进入APP不等于异常环境已正确，IROM链接地址和运行时VTOR必须同时匹配；STOP再次调用SystemInit也要保持该偏移。

#### 静态检查发现：DMA错误可能被误报超时

- **证据：**旧等待代码查询TE硬件标志，ISR却已清TE并把RxResult写成2。
- **判断：**存在错误报告丢失路径，未记录实际触发TE的故障实验，因此属于代码检查发现，不是用户实测Bug。
- **修改：**等待函数改为检查RxResult==2并保存DMA错误类型；此逻辑已存在于当前源码。

#### 问题五：OLED加入后复位卡住，Boot与APP重叠

- **现象：**复位后OLED停住、没有串口或超时跳转，重新下载才能再次使用。
- **证据：**当时Map加载区大小0x4124=16676，Boot允许0x8000，而APP从0x08004000；超出16KiB的292字节落入APP开头。
- **已确认配置问题：**分区重叠；下载Boot可能覆盖APP，APP擦除/下载可能破坏Boot尾部。具体复位卡住指令未捕获，不声称精确指令级根因。
- **处理方案：**限制Boot为0x4000，优化编译/裁剪资源，再重新下载两个工程；添加首日志于OLED初始化前便于定位。
- **现有产物：**Map加载0x3500=13568，最大0x4000，已在分区内。但当前EIDE仍是0x8000且level-0，不能记成两套配置已一致；复位与升级全流程回归仍需明确确认。

#### 问题六：进度前导零及显示代码占用

- **现象：**固定3位OLED_ShowNum把70显示为070%；使用OLED_Printf后用户报告空间不足。
- **处理方案：**用1/2/3位条件显示替代Printf；去掉Boot不需要的12×24字体、中文解析、游戏图片，保留完整ASCII 8×16与6×8。
- **当前源码差异：**ShowProgress仍调用3位ShowNum；OLED_ShowChar仍引用OLED_F12x24，ShowString仍引用中文表。因此上述精简和无前导零方案未在本次读取代码中确认落地，不归档为已完成。
- **经验：**注释文字本身不占Flash；只有移除被链接的代码/数组及其引用才能省空间。不能删ASCII数组中间条目，否则Char-' '索引错位。
